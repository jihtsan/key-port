# KeyPort 整体重构与迁移计划

- 状态：提案
- 文档版本：V2.0
- 日期：2026-08-28
- 关联 Issue：[GitHub #26](https://github.com/jihtsan/key-port/issues/26)
- 目标架构：[Graph 拓扑与跨设备授权架构](./Graph拓扑与跨设备授权架构.md)

## 1. 改版决策

可以果断替换当前 UI，也应该删除已经固化旧心智模型的界面和编排代码；但不建议同时重写已经建立安全约束的 SSH、Host Key、Keychain 和远端文件更新实现。

本次重构采用以下策略：

- **UI 全量替换**：Graph 成为默认工作区，节点列表成为辅助视图，现有服务器/密钥/设备四块并列导航退出主信息架构。
- **领域模型重建**：拆分 `ServerConnection`，用远端资源、访问配置、设备身份和密钥授权表达真实关系。
- **应用层重建**：拆掉 1116 行的集中式 `AppModel`，用接入、访问、拓扑和同步四个深模块承载行为。
- **安全核心迁移复用**：把现有 SSH 和 Keychain 能力收进新 seam，先保留实现，再根据真实环境验证决定是否替换底层。
- **数据有迁移、旧 UI 无兼容负担**：已有用户数据必须迁移；旧页面结构、旧选择状态和旧工具栏行为不承诺保留。

这不是在现有页面上增加一个 Graph 标签页。Graph 将成为新的产品结构，旧列表 UI 只在迁移期间短暂存在。

## 2. 当前实现评估

### 2.1 可保留的基础

现有版本已经建立了几条正确且有价值的安全路径：

- Host Key 在密码或公钥认证之前确认，变化时阻断。
- 密码通过 Keychain 和一次性 FIFO/AskPass 进入系统 OpenSSH，不进入参数和普通 stdin。
- `authorized_keys` 注入按公钥 blob 去重，保留未知项，备份后原子替换并复验。
- 每台设备拥有独立 SSH 密钥，CloudKit 上传前剥离私钥路径和 Agent 状态。
- SSH Config 写入使用 KeyPort 专用文件和幂等 Include。
- 核心解析器、Host Key 判定和密码验证 gate 已可独立测试。

这些能力应当成为新 `AccessCoordinator` 后面的实现资产，而不是因 UI 改版而重写。

### 2.2 主要结构问题

| 现状 | 问题 | 目标处理 |
| --- | --- | --- |
| `ServerConnection` 同时保存资源、入口、账号、信任和检查状态 | 无法表达一个资源的多个账号、服务和多设备关系 | 拆为 `RemoteResource`、`AccessProfile`、`HostTrust`、`AccessObservation` |
| `AuthorizationStatus` 是单一状态枚举 | 网络失败、Host Key、密码、密钥和同步互相覆盖 | 改为多个独立状态维度，由 Graph 投影摘要 |
| `AppSnapshot` 聚合所有实体和运行状态 | 任意局部修改都触碰整份快照，迁移和冲突粒度过大 | 使用规范化实体、本地事务和设备本地观测 |
| CloudKit 使用一个 `keyport-metadata-v1` payload | 多设备并发只能整包合并，容易丢字段且难诊断 | 改为自定义 Zone 中的实体级记录和增量同步 |
| `AppModel.swift` 1116 行 | 导航状态、表单、SSH、Keychain、同步、迁移和审计集中在一个对象 | 拆为深应用模块和轻量 Feature Model |
| `NavigationSplitView` 以服务器、密钥、设备、日志分类 | 用户必须在多个列表中拼装“谁能访问谁” | Graph 默认展示关系，Inspector 汇总细节 |
| 密钥和设备是独立顶层页面 | 它们与目标资源的授权关系不直观 | 设备成为 Graph 节点，密钥成为设备安全细节 |
| 添加服务器后立即触发密码检查 | 草稿、Host Key、凭据证明和保存的事务边界不清楚 | 使用可恢复的 `EnrollmentSession` 明确分步流程 |
| UI 分别暴露“密码检查”“密钥检查”“授权” | 用户需要理解内部步骤，动作名称重复 | 收敛成“验证并添加”和“启用密钥访问” |

## 3. 目标 UI 信息架构

### 3.1 主窗口

```text
┌─────────────────────────────────────────────────────────────────────┐
│ Toolbar: 添加节点 | 视图模式 | 搜索/过滤 | 同步状态 | 当前任务      │
├──────────────┬───────────────────────────────────┬──────────────────┤
│ Sidebar      │ Graph Canvas / Node List          │ Inspector        │
│              │                                   │                  │
│ Graph        │ 当前设备 / 全部设备 / 服务拓扑    │ 概览             │
│ Nodes        │                                   │ 访问             │
│ Activity     │ 节点、边、分组、空状态和操作进度  │ 服务             │
│              │                                   │ 历史             │
└──────────────┴───────────────────────────────────┴──────────────────┘
```

侧边栏只保留三个工作入口：

- **Graph**：默认入口，查看设备、远端资源、服务和关系。
- **Nodes**：可排序、可批量选择的等价列表，适合大量节点、键盘和 VoiceOver。
- **Activity**：当前操作、失败项和本机审计事件。

Settings 继续使用独立 Scene。密钥和设备不再作为与服务器平级的长期侧边栏页面。

### 3.2 Graph 画布

- 当前设备视图默认将当前 Mac 放在视觉中心。
- 远端资源节点显示名称、环境、主要服务和综合访问摘要。
- 边的标签显示账号或 SSH 别名；点击边直接打开对应访问配置。
- 其他设备默认弱化，切换“全部设备”后显示完整授权差异。
- 服务节点默认折叠在远端资源中；服务拓扑视图再全部展开。
- 支持框选、缩放、平移、自动布局、固定位置、搜索和仅看异常。
- 所有 Graph 信息都必须在 Nodes 列表和 Inspector 中有文本等价表达。

### 3.3 Inspector

选中远端资源时提供：

1. **概览**：资源名称、类型、环境、标签和备注。
2. **访问**：所有访问配置、当前设备密钥访问、其他设备授权和 Host Key。
3. **服务**：托管服务与依赖关系。
4. **历史**：本地观测、授权变更和同步冲突。

选中设备时提供设备公开信息、SSH 身份和到各资源的授权；选中边时直接显示访问配置、最近观测和状态对应的主操作。

### 3.4 新增流程

新增使用一个分步 Sheet，而不是保存后再从详情页寻找多个按钮：

1. 资源与 SSH 入口。
2. 网络预检和 Host Key 确认。
3. 账号密码或已有密钥验证。
4. 验证并添加。
5. 可选立即“启用密钥访问”。

表单关闭前保留本地草稿；未经验证的记录只有在用户明确选择“保存为待处理”时才进入工作区。

### 3.5 主要动作命名

| 旧动作 | 新动作 | 说明 |
| --- | --- | --- |
| Add Server | 添加远端资源 | 同时建立第一个访问配置 |
| Check Password SSH | 验证账号密码 | 只证明账号可控，不等于密钥授权 |
| Check Key SSH | 验证密钥访问 | 复查当前设备身份 |
| Authorize This Mac | 启用密钥访问 / 授权当前设备 | 已有授权时只验证，无授权时安装公钥 |
| Sync Metadata | 同步工作区 | 同步 Graph 元数据，不暗示密码或私钥都已同步 |

## 5. 模块设计

### 5.1 `TopologyCatalog`

负责工作区实体的一致性和查询。外部只需要提交领域命令并读取版本化快照；重复检测、引用完整性、删除标记和本地事务都留在模块内部。

UI 不应直接修改实体数组，也不应知道本地最终使用 SwiftData、SQLite 还是 JSON 适配器。

### 5.2 `EnrollmentCoordinator`

负责一个可暂停和恢复的接入状态机。界面向它提供用户输入，模块返回下一步、需要确认的 Host Key、凭据请求或最终结果。

DNS/TCP、Host Key、密码认证和提交事务属于同一个行为，不再由 View 或根状态对象手工排序。

### 5.3 `AccessCoordinator`

对外暴露三个高层意图：

- 确保当前设备具有密钥访问。
- 验证现有密钥访问。
- 撤销一个明确的密钥授权。

身份生成/选择、LocalAuthentication、Keychain、远端文件、复验、SSH Config 和审计属于其内部实现。测试与 UI 都通过这一个 interface 观察结果和进度。

### 5.4 `GraphProjector`

这是纯进程内模块。输入领域快照、本地观测和视图查询，输出稳定的 `GraphSnapshot`。布局算法可作为内部策略，但节点和边的语义不能由 SwiftUI View 临时拼装。

### 5.5 `SyncCoordinator`

负责本地 outbox、CloudKit 增量、冲突和同步报告。它同步领域实体，不接收整个 UI 状态，也不读取私钥和密码值。

## 7. V3 → V4 数据迁移

### 7.1 字段映射

| V3 | V4 |
| --- | --- |
| `ServerConnection.id` | 保留为第一个 `AccessProfile.id`，避免 Keychain account 失联 |
| `ServerConnection.name` | 新建 `RemoteResource` 的名称 |
| `ServerConnection.group` | 原样保留为 `RemoteResource.tags` 中的迁移标签；不擅自推断环境 |
| `host/port/username/alias/notes` | `AccessProfile` |
| `confirmedHostKeys` | `HostTrust` 历史 |
| `status/passwordCheck/keyCheck/lastCheckedAt` | 当前设备 `AccessObservation`；不进入共享实体 |
| `Device` | `DeviceNode`，ID 原样保留；`isCurrent` 转成本地映射 |
| `SSHKeyRecord` | `SSHIdentity` + 当前设备 `LocalIdentityPresence` |
| `Authorization` | `KeyGrant`，旧 `serverID` 映射到 `AccessProfile.id` |
| `AuditEvent` | 本地 Activity 记录 |
| `isDeleted` | `deletedAt` tombstone |

每个旧 `ServerConnection` 默认创建一个独立 `RemoteResource`，资源 ID 由旧 server ID 确定性派生。即使两个旧连接地址相似，也只生成合并建议，不在迁移中自动合并，避免把不同账号、端口或环境错误归为一台资源。

### 7.2 本地迁移步骤

1. 以只读方式加载并校验 V3 快照。
2. 在应用支持目录创建带时间和校验值的 V3 备份。
3. 在内存中执行确定性映射和引用完整性检查。
4. 将 V4 写入临时存储并重新读取验证。
5. 原子切换活动 schema，记录 migration marker。
6. 首次启动展示迁移摘要：资源、访问配置、设备、身份、授权和冲突数量。
7. 一个发布周期内保留 V3 备份和只读解码能力。

任何一步失败都继续使用原 V3 数据，不允许部分切换。

### 7.3 CloudKit 迁移步骤

1. 迁移前先拉取并合并旧 `keyport-metadata-v1` payload。
2. 将合并结果按 V4 实体上传到新的私有 Zone。
3. 写入包含实体数量和摘要校验值的 `KPWorkspace` migration marker。
4. 重新拉取并验证引用和数量后，才将本机切换到 V4 同步。
5. 旧 payload 至少保留一个版本且不再由 V4 客户端覆盖。
6. 如果迁移后检测到旧客户端仍更新 V3 payload，Activity 显示兼容性警告并提供显式重新导入，不能静默覆盖 V4。

工作区升级后不支持 V3 与 V4 客户端长期双向写入。升级界面应列出最近活跃设备并提醒先更新其他 Mac。

## 8. 分阶段实施

每个阶段单独建立 Issue、分支和 PR，避免一个无法评审的大改分支。

### 阶段 0：设计基线

- 领域词汇、Graph 架构、同步边界、迁移方案和 ADR。
- 不修改运行代码。

完成条件：术语一致，现状与目标映射清楚，后续 Issue 可从本文拆分。

### 阶段 1：V4 Domain 与迁移器

- 新实体、正交状态和 Graph 投影。
- V3 fixture 与确定性迁移测试。
- 内存存储适配器和 `TopologyCatalog`。

完成条件：不接 UI 也能构建 V4 工作区并生成可断言的 Graph 快照。

### 阶段 2：接入与密钥访问编排

- `EnrollmentCoordinator` 状态机。
- `AccessCoordinator` 的确保、验证和撤销操作。
- 现有 OpenSSH、Keychain、Host Key、SSH Config 实现改造成适配器。

完成条件：自动测试覆盖已有密钥、密码授权、Host Key 阻断、部分失败和取消；真实 Linux 环境补齐安全矩阵。

### 阶段 3：新 UI 骨架和 Graph

- Workspace、Graph、Nodes、Inspector 和 Activity。
- 新增远端资源流程和单节点“启用密钥访问”。
- Graph 与列表的键盘、VoiceOver 和 Reduce Motion 等价体验。

完成条件：用户不进入旧页面即可完成单设备本地闭环。

### 阶段 4：V4 CloudKit 与多设备

- 自定义 Zone、实体级记录、outbox、change token 和冲突。
- iCloud Keychain 凭据定位与新设备批量授权。
- 双 Mac 真实环境验收。

完成条件：Mac 1/Mac 2/A/B/C 场景通过，离线修改和冲突不会丢失安全关键字段。

### 阶段 5：切换与清理

- 执行本地和 CloudKit 迁移。
- 默认启用新 UI，删除旧页面和旧 AppModel。
- 删除仅服务于 V3 运行路径的迁移辅助逻辑。
- 更新归档、文档、截图和发布检查。

完成条件：代码中不存在双重领域事实源；旧 UI 和 V3 写路径被彻底移除。

### 阶段 6：服务拓扑增强

- 托管服务、依赖关系、自定义布局和高级过滤。
- 根据实际节点规模验证布局性能和交互。

完成条件：服务关系不影响 SSH 安全主流程，100+ 节点仍可浏览和检索。

## 9. 删除门槛

只有满足以下条件后才删除旧 UI 和 `AppModel`：

1. V3 迁移 fixture、失败回滚和摘要验证通过。
2. 新 UI 覆盖新增、编辑、删除、验证、授权、撤销、同步、导入导出和错误恢复。
3. 新 Graph 的所有信息存在 Nodes/Inspector 文本替代。
4. SSH Config、Host Key、Keychain 和 AskPass 回归检查通过。
5. 新 CloudKit 模型通过至少两台 Mac 的同步和冲突测试。
6. 打包、签名、启动和 Release 构建通过。

达到门槛后应直接删除旧 Feature 文件和相关测试，不保留永久的“Legacy Mode”。

## 10. 验证矩阵

### 10.1 自动检查

- Domain：实体不变量、正交状态、去重和 tombstone。
- Enrollment：每个状态转移、Host Key 拒绝、密码失败、已有密钥路径和取消。
- Access：幂等安装、复验失败、撤销、缺少本地私钥和远端漂移。
- Graph：同一资源多个账号、多设备独立授权、服务折叠和状态优先级。
- Migration：真实 V3 fixture、重复运行、损坏输入、原子回滚和 Keychain ID 保持。
- Sync：并发编辑、删除复活、Host Key 冲突、离线 outbox 和布局冲突。
- Security：日志与序列化数据不含密码/私钥。

### 10.2 真实环境

- 两台登录同一 Apple ID 的 Mac。
- 至少两台隔离 Linux/OpenSSH 目标，覆盖 Ed25519/RSA 和常见服务器策略。
- iCloud 可用、关闭、延迟和账号退出。
- iCloud Keychain 同步开启/关闭及密码更新。
- Host Key 轮换、网络中断、并发修改 `authorized_keys` 和应用强制退出。
- 最终 `ssh <alias>` 在两台 Mac 上分别使用各自私钥成功登录。

## 11. 主要风险与控制

| 风险 | 控制 |
| --- | --- |
| Graph 节点变多后失去可读性 | 多种投影、过滤、折叠、Nodes 列表和自动布局 |
| 用户把连线误解为网络路由 | 关系类型明确命名，不自动推断，Inspector 展示证据来源 |
| CloudKit 并发覆盖安全字段 | 实体级记录、安全字段显式冲突、Host Key 历史追加 |
| 新 Mac 误以为继承了访问权 | 当前设备状态只由本地身份和实时观测决定 |
| 全量改 UI 同时破坏安全流程 | 安全实现先适配后复用，通过应用层 interface 验证 |
| V3/V4 设备并存造成分叉 | 工作区升级门槛、活跃设备提示和旧写入检测 |
| “服务”范围无限扩大 | 首版只保存名称、类型、所属资源和逻辑关系，不执行服务命令或监控 |
